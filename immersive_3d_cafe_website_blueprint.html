1. Product brief

Product goal: Build a premium, mobile-first cafe website whose visual language is derived from the actual physical cafe, while enabling customers to discover the cafe, browse its menu, place orders and make reservations. Give the owner a protected admin area to operate the digital storefront.

Customer-facing experience

  • Memorable branded landing page
  • Optional interactive 3D moments
  • Menu, product details and customization
  • Cart, checkout and payment
  • Pickup/delivery choice where supported
  • Reservation request or confirmed booking
  • Contact, location, opening hours and FAQs

Owner-facing operations

  • Secure admin login and roles
  • Menu, pricing and availability management
  • Order queue and status updates
  • Reservation management
  • Offers and content management
  • Basic sales and order reporting
  • Audit trail for important changes

Out of scope for initial release unless explicitly requested: multi-branch franchise management, native iOS/Android apps, complex loyalty points, live driver GPS, POS hardware integration, accounting integrations and automated ingredient-level inventory deduction. Design the architecture so these can be added later.

2. Product principles

  1. Brand authenticity: derive colors, typography, imagery, materials and 3D environment from the actual cafe, not a generic cafe template.
  2. Commerce first: users must still find the menu, add items and complete checkout if WebGL fails or is disabled.
  3. Progressive enhancement: load a lightweight page first; load 3D assets only where needed.
  4. Mobile-first: provide a simplified, performant mobile treatment rather than forcing desktop-scale 3D scenes onto phones.
  5. Owner autonomy: routine content and menu changes must not require code deployments.
  6. Truthful availability: never show an item, slot or order state as available unless the backend confirms it.
  7. Accessible interaction: provide keyboard-operable controls, readable contrast, reduced-motion support and non-3D alternatives.

3.2 Commerce rules

  • Prices, taxes, discounts and totals are calculated and validated on the server. Never trust totals submitted by the browser.
  • Each cart line stores product ID, selected variant, add-ons, quantity and a price snapshot for the order record.
  • Re-check item availability and current price during checkout.
  • Use a unique order number and idempotency protection to prevent duplicate orders from repeated payment callbacks or user retries.
  • Order states should be controlled transitions, for example: pending_payment → placed → accepted → preparing → ready → completed. Include cancelled and payment_failed where appropriate.
  • Do not mark an order as paid based only on the frontend redirect. Verify the payment provider's signed webhook on the backend.
  • Make fulfilment modes explicit: pickup, dine-in or delivery only if the cafe actually supports them. Delivery needs service zones, fees, minimum order and address validation.

4. Main user journeys and business flows

4.1 Customer order flow

Visit home→Browse menu→Select item/options→Add to cart→Checkout→Server validates→Payment→Order confirmation
  1. Customer selects products and valid modifiers.
  2. Frontend sends product IDs, option IDs, quantities and fulfilment choice—not a trusted final amount.
  3. Backend loads current prices, verifies active status, stock/availability, coupon rules, tax and fees.
  4. Backend creates a pending order and payment attempt, then requests a payment session from the provider.
  5. Customer completes payment through the provider's hosted/secure flow.
  6. Backend verifies the signed webhook, updates payment and order status once, and emits an order event.
  7. Customer sees a confirmation page and receives an email/SMS/WhatsApp notification only if that channel is configured.
  8. Admin sees the new order and updates its preparation status.

4.2 Reservation flow

Choose date→Party size→Available slot→Contact details→Create booking→Owner confirms

Availability must be computed on the server using opening hours, table/seat capacity, slot duration, existing confirmed bookings and any blackout periods. Prevent overbooking with a database transaction or appropriate locking/constraint strategy. Decide with the owner whether bookings are instantly confirmed or require manual approval.

4.3 Owner menu update flow

Admin login→Edit product→Validate/save→Database update→Website reflects update

Use server-side cache revalidation or short-lived caching so changes appear promptly. If product models/images are changed, store media metadata and update the product's media reference; do not require a frontend rebuild.

5. Visual system and 3D experience

5.1 Translate the real cafe into the website

Collect the cafe logo and brand guide, exterior/interior photographs, counter and seating details, menu photography, packaging/cup design, materials, lighting references and the owner's preferred mood. Create a visual reference board before styling the site.

Branded cups/packagingHero object and product model details
Signature menu itemFeatured product story and 3D showcase
Signage and typographyLogo placement, headings and UI typography

5.2 Suggested page composition

  1. Hero: concise headline, location/brand statement, primary “Explore menu” CTA, one signature 3D object or scene.
  2. Signature selection: real product photography first; optional 3D model viewer for selected products.
  3. Brand story: editorial photography, short narrative and subtle scroll transition.
  4. Menu preview: clear categories and prices; do not hide core menu navigation behind 3D interactions.
  5. Visit the cafe: location, hours, atmosphere gallery and reservation CTA.
  6. Footer: contact, socials, policies and business details.

5.3 3D interaction rules

  • Use 3D to explain or reinforce the brand, not to obstruct the customer task.
  • Limit the initial page to one main 3D scene. Load additional models on demand or when their section approaches the viewport.
  • Use compressed GLB/glTF where suitable; prefer Draco mesh compression and KTX2/Basis textures when the pipeline supports them.
  • Set sensible polygon, texture and draw-call budgets. Remove hidden meshes, unused materials, excessive lights and unnecessary animation tracks.
  • Use baked lighting where possible. Avoid expensive real-time shadows and post-processing on low-end mobile devices.
  • Pause animation when the tab is hidden or the scene is off-screen. Respect prefers-reduced-motion.
  • Provide a poster image/fallback if WebGL is unavailable, the model fails or the device is underpowered.
  • Ensure 3D controls do not cover navigation, menu links, cart or accessibility controls.

6. Integrating the 3D assets already downloaded

Before implementation, create an inventory. Do not rename, convert or delete original files until a backup exists.

6.1 Asset audit

  1. Collect all assets into a single working folder and retain the original archive as a backup.
  2. Record filename, format, file size, dimensions, polygon count if available, texture size, animation presence, license/source and intended page section.
  3. Preview each asset in Blender or a glTF viewer. Check orientation, scale, pivot/origin, materials, texture paths, transparency and animation.
  4. Check the license permits commercial website use and confirm whether attribution is required. “Downloaded” does not automatically mean commercially licensed.
  5. Identify duplicate, unused, broken or excessively large assets.

6.4 Example React Three Fiber model component

import { Suspense } from "react";
import { Canvas } from "@react-three/fiber";
import { Environment, Html, useGLTF } from "@react-three/drei";

function CoffeeModel() {
  const { scene } = useGLTF("/models/hero/coffee-cup.glb");
  return <primitive object={scene} scale={1.4} position={[0, -0.6, 0]} />;
}

export function HeroScene() {
  return (
    <div className="hero-scene" aria-label="Decorative 3D coffee cup">
      <Canvas dpr={[1, 1.5]} camera={{ position: [0, 0, 4], fov: 38 }}>
        <ambientLight intensity={1.1} />
        <directionalLight position={[3, 4, 5]} intensity={1.5} />
        <Suspense fallback={null}>
          <CoffeeModel />
          <Environment preset="studio" />
        </Suspense>
      </Canvas>
    </div>
  );
}

useGLTF.preload("/models/hero/coffee-cup.glb");

Illustrative starter only. Tune scale, camera, lighting, environment, loading state and accessibility to the actual model. For production, add an error boundary, device capability check, reduced-motion behavior, visibility-based pause and a static fallback. Do not render a full-screen Canvas for every small product card.

7. Recommended technical architecture

For a first release, keep the system modular but avoid unnecessary microservices. A single web application and a well-structured backend are easier to ship and operate.

Web application

Next.js + TypeScript

  • Public pages and SEO
  • Admin dashboard
  • React Three Fiber scenes
  • Cart and checkout UI
  • Responsive components

Backend

NestJS + TypeScript

  • REST API
  • Business rules and validation
  • Authentication and authorization
  • Payment webhooks
  • Order and reservation workflows

Data and media

PostgreSQL + Prisma

  • Relational business data
  • Database migrations
  • Object storage for images/models
  • CDN delivery for static assets

External services

Provider-based integrations

  • Razorpay or other locally suitable payment provider
  • Email/SMS provider if required
  • Maps link/embed
  • Error monitoring and analytics

10. Phase-wise development plan

Indicative sequencing for a small focused team. Estimates depend on asset quality, design approval, payment/reservation complexity and the amount of content the cafe owner supplies. A solo developer should add contingency.

Tasks

  • Meet owner and confirm business model, target customers and success measures.
  • Collect brand assets, cafe photographs, menu, prices, hours, contact and policies.
  • Confirm order types, delivery boundaries, taxes, cancellation/refund rules and payment provider.
  • Confirm reservation policy, table capacity, slot duration and manual/instant confirmation.
  • Audit downloaded 3D assets and commercial-use licenses.
  • Write acceptance criteria and freeze MVP scope.
Deliverables: approved requirements, asset inventory, risk register, MVP backlog.
Phase 1 — UX, brand system and technical foundation3–5 days

Tasks

  • Create sitemap, page wireframes and customer/admin flows.
  • Define colors, typography, spacing, buttons, cards and responsive breakpoints.
  • Create high-fidelity home, menu, product, cart, checkout and admin mockups.
  • Choose 3D moments and static fallbacks for each.
  • Set up repositories, linting, formatting, TypeScript, CI checks and environment templates.
  • Set up local PostgreSQL, Prisma and initial migrations.
Exit gate: owner approves the visual direction and the main user journeys.
Phase 2 — Core frontend and content experience4–7 days

Tasks

  • Build shared layout, navigation, footer and responsive design tokens.
  • Build home, story, visit/contact, menu and product detail pages.
  • Connect menu pages to API data rather than hard-coded production content.
  • Implement loading, empty, error and unavailable states.
  • Add SEO metadata, sitemap, robots rules and structured business data where accurate.
  • Verify core pages are usable with JavaScript/3D disabled as far as the framework allows.
Exit gate: all public content pages work with real sample data across mobile and desktop.
Phase 3 — 3D asset integration and motion3–7 days

Tasks

  • Convert/optimize selected source models to web-ready formats where required.
  • Integrate the hero model using a lazy-loaded scene and static poster fallback.
  • Implement lighting, camera framing, material tuning and responsive scene sizing.
  • Add restrained pointer interaction and scroll-triggered motion.
  • Add model loading progress, error boundary and WebGL/device fallback.
  • Implement reduced-motion and off-screen animation pause.
  • Profile frame rate, memory and network payload on desktop and mobile.
Exit gate: 3D is visually approved and does not block navigation, menu or checkout.
Phase 4 — Backend, database and admin6–10 days

Tasks

  • Implement authentication, session handling and role-based authorization.
  • Build menu/category/product and option management.
  • Build order creation, server-side pricing and order state transitions.
  • Build admin order queue and reservation management.
  • Build content/settings management for cafe details and hero content.
  • Add audit logs, pagination, validation, rate limiting and error handling.
  • Seed staging with owner-approved sample menu and settings.
Exit gate: owner can manage menu and orders without editing code or database manually.
Phase 5 — Checkout, payments and reservations4–8 days

Tasks

  • Implement cart persistence and server-side quote validation.
  • Integrate payment provider in sandbox mode.
  • Verify signed webhooks, idempotency and duplicate callback behavior.
  • Implement payment success, failure, pending and retry experiences.
  • Implement reservation availability and overbooking protection.
  • Configure customer/admin notifications if required and approved.
  • Test refunds/cancellations and reconcile provider transactions with orders.
Exit gate: complete sandbox purchase and reservation scenarios pass end-to-end.
Phase 6 — QA, accessibility, performance and owner acceptance4–6 days

Tasks

  • Run automated unit, integration and end-to-end tests.
  • Test supported browsers, screen sizes and real devices.
  • Run accessibility checks and keyboard-only navigation.
  • Run Lighthouse and Core Web Vitals checks; optimize images, fonts and 3D payload.
  • Test security controls, role boundaries, webhooks and input validation.
  • Run owner UAT using realistic orders, menu changes and reservations.
  • Fix launch-blocking defects and document known limitations.
Exit gate: no open critical/high-severity defects; owner signs off on content and workflows.
Phase 7 — Production deployment and launch2–4 days

Tasks

  • Provision production hosting, database, object storage and CDN.
  • Configure domain DNS, TLS, environment secrets and production payment credentials.
  • Run reviewed database migrations and take a pre-launch backup.
  • Deploy application and verify health checks.
  • Run smoke tests: menu, checkout, webhook, admin, reservations and mobile fallback.
  • Enable error monitoring, uptime monitoring, logs and backup alerts.
  • Train owner/staff and hand over runbook and support process.
Exit gate: production smoke tests pass and owner confirms readiness to accept real orders.
Phase 8 — Stabilization and iterationFirst 2 weeks
  • Monitor payment/order mismatches, failed requests, slow pages and user feedback.
  • Review analytics for menu discovery and checkout drop-off.
  • Fix defects and tune performance without destabilizing checkout.
  • Prioritize next features based on owner feedback and real customer behavior.

11.2 Essential test scenarios

  • Menu displays only active/available items and correct prices.
  • Unavailable item cannot be ordered by manipulating the browser request.
  • Server rejects invalid modifiers, quantities, coupon codes and stale prices.
  • Double-click/retry does not create duplicate paid orders.
  • Invalid or unsigned payment webhook cannot mark an order paid.
  • Valid webhook is processed once, even if delivered more than once.
  • Payment failure leaves an understandable retry/cancel state.
  • Admin-only endpoints reject customers and unauthenticated visitors.
  • Staff role cannot access settings or actions beyond assigned permissions.
  • Concurrent reservation requests cannot exceed configured capacity.
  • Timezone and daylight-saving behavior is correct for the cafe's location.
  • 3D asset missing, slow, malformed or unsupported does not break the page.
  • Reduced-motion setting disables non-essential movement.
  • Cart, menu and checkout remain usable on small screens and slow networks.
  • Database restore procedure has been tested, not merely configured.

12. Security, privacy and reliability

  • Store secrets only in deployment secret management/environment variables. Commit only .env.example.
  • Hash passwords with a modern password hashing algorithm if managing passwords directly; use secure, HTTP-only, same-site cookies for sessions.
  • Enforce authorization on the backend for every admin route and object-level operation.
  • Validate and sanitize all input; use ORM parameterization; escape user-generated content.
  • Verify payment webhook signatures and amount/currency/order references.
  • Apply rate limits to login, public order creation, coupon validation and reservation endpoints.
  • Minimize customer data collection. Publish a privacy policy and define retention/deletion practices appropriate to applicable law.
  • Use HTTPS everywhere, secure headers, dependency scanning and least-privilege database credentials.
  • Back up the database automatically and test restoration on a schedule.
  • Log operational events without writing passwords, payment secrets or unnecessary personal data to logs.
Payment compliance: prefer the payment provider's hosted checkout or approved SDK. Do not store card numbers, CVV or raw payment credentials. Confirm the provider's current integration and compliance requirements before production.

13. Deployment plan

13.1 Practical deployment topology

Customer browser→CDN / HTTPS→Next.js web app→NestJS API→PostgreSQL

Serve images and optimized 3D files from object storage behind a CDN. Keep the API and database private where the hosting platform supports private networking. The specific cloud provider can be selected after expected traffic, budget, team familiarity and operational ownership are known.

13.2 Deployment options

  • Managed-first: deploy the web app to a managed Next.js platform, API to a managed container service, PostgreSQL to a managed database, and assets to object storage/CDN. This reduces operational burden.
  • Containerized cloud/VPS: use Docker images for web and API, reverse proxy, managed or separately backed-up PostgreSQL, object storage/CDN and automated TLS. This offers more control but requires patching, monitoring and backup discipline.

13.3 CI/CD pipeline

  1. On pull request: install dependencies, lint, type-check, run unit tests and build.
  2. Run API integration tests against an ephemeral/test database where practical.
  3. On merge to main: build immutable web/API artifacts and deploy to staging.
  4. Run migrations as a controlled release step, then staging smoke tests.
  5. Require approval before production deployment.
  6. Deploy production, run health checks and smoke tests, then monitor error rate and key flows.
  7. Keep a documented rollback plan. Database migrations should be backward-compatible where possible; a code rollback does not automatically reverse a destructive schema migration.

13.4 Production checklist

  • Domain and DNS verified; HTTPS certificate active.
  • Production secrets set and sandbox credentials removed.
  • Database backups and restore process verified.
  • CDN cache policy configured for models, images and app assets.
  • Webhook endpoint publicly reachable over HTTPS and signature verification enabled.
  • Admin account created securely; default/demo credentials removed.
  • Monitoring, error reporting, logs and uptime checks active.
  • Legal pages, business details, opening hours and policies approved by owner.
  • Real payment tested with a low-value controlled transaction if provider/business process permits.
  • Staff trained on order queue, refunds/cancellations and reservation workflow.

14. Definition of done / acceptance criteria

Customer experience

  • Site reflects the cafe's approved identity and real information.
  • Menu is manageable from the admin dashboard and updates appear on the public site.
  • Customer can complete the supported ordering flow on mobile and desktop.
  • Payment status is based on verified backend confirmation.
  • Reservation rules prevent overbooking, if reservations are in scope.
  • 3D elements load progressively and have graceful fallbacks.
  • Core content and commerce remain accessible without 3D.

Owner operations

  • Authorized owner/staff can manage products, availability and orders.
  • Unauthorized roles cannot access protected actions.
  • Owner can update relevant website content without a code change.
  • Errors and important actions are observable and supportable.

Release quality

  • Critical end-to-end flows pass in staging.
  • No known critical/high-severity launch blockers remain.
  • Performance and accessibility have been checked on representative devices.
  • Backup restore, deployment and rollback procedures are documented.
  • Owner has approved production content and signed off on UAT.
